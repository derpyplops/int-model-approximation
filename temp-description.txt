This document proposes an experiment to train an int32 “proof model” to emulate an fp8 “production model.”

---

## Motivation

Proving floating-point model execution directly seems expensive. In particular, if we want to use Freivalds-style checks over float computations, we either need to range-check aggressively or eat a large overhead. The range checks themselves can expose adversarial entropy / nondeterminism that we would rather not introduce. So the simpler path is: keep the production model in floats, create a separate high-precision integer “proof model,” and train that proof model to emulate the production model closely enough that the divergence is small.

This experiment does **not** need to involve ZKPs. The only question for now is empirical:

> Given a float model, can we turn it into an int32/fixed-point model and train that int32 model so that its intermediate matmul outputs and final logits become very close to the float model’s?
> 

## Core experiment

1. Start with a frozen float model.
2. Build an int32/fixed-point version of the same model.
3. Train the int32 model to emulate the float model.
4. Measure whether the int32 model’s outputs converge toward the float model’s outputs over training.

The main thing to plot is divergence in logits over training time, but we should also track per-layer / per-matmul divergence so we can see where the mismatch is coming from.

## Setup

Use one small-to-medium model where iteration time is low enough that we can run several variants quickly.

The float model is the teacher, $f_{\text{float}}(x)$, and the int32 model is the student / proof model, $f_{\text{int32}}(x)$.

The int32 model should use the same architecture initially. It is fine if the implementation uses fake quantization / straight-through gradients internally, as long as evaluation uses the actual intended int32/fixed-point path.

The first version should keep this boring:

- same tokenizer / inputs;
- same architecture;
- frozen float teacher;
- trainable int32 student;
- deterministic eval;
- no ZKP/prover integration.

## Training target

I think the most direct loss is at the per-matmul-output level, plus optionally the final logits.

For each matmul or major linear operation $i$, collect the float teacher output $M^i_{\text{float}}(x)$ and the int32 student output $M^i_{\text{int32}}(x)$.

Train with something like:

$$
\mathcal{L} = \sum_i \alpha_i \left\| M^i_{\text{int32}}(x) - M^i_{\text{float}}(x) \right\|_1 + \beta \left\| z_{\text{int32}}(x) - z_{\text{float}}(x) \right\|_1
$$

or the same thing with L2. Here $z$ is the final logit vector.

A reasonable first pass is:

$$
\mathcal{L} = \sum_i \left\| M^i_{\text{int32}} - M^i_{\text{float}} \right\|_2^2 + \left\| z_{\text{int32}} - z_{\text{float}} \right\|_2^2.
$$

No need to optimize the loss too much initially. The main question is whether the curve moves.

## Variants to run

Run a few simple variants:

| **Variant** | **Description** | **Purpose** |
| --- | --- | --- |
| Naive int32 | Convert float model to int32, no training | Baseline divergence |
| Train weights only | Train int32/fixed-point weights to match float outputs | Main experiment |
| Train weights + scales | Also train per-layer or per-channel scales | Tests whether scaling is the bottleneck |
| Per-matmul loss only | Match intermediate matmul outputs | Tests local emulation |
| Per-matmul + logits loss | Match intermediate outputs and final logits | Likely best default |

No need to try exotic architectures yet. Start with same architecture.

## Metrics to plot over training

Main plots:

1. **Logit L1 over training steps:** $\| z_{\text{int32}} - z_{\text{float}} \|_1$.
2. **Logit L2 over training steps:** $\| z_{\text{int32}} - z_{\text{float}} \|_2$.
3. **Mean absolute logit error:** $\frac{1}{V} \sum_j |z_{\text{int32},j} - z_{\text{float},j}|$, where $V$ is vocab size.
4. **Max logit error:** $\max_j |z_{\text{int32},j} - z_{\text{float},j}|$.
5. **Per-matmul output L1/L2:** for each major matmul, plot $\| M^i_{\text{int32}} - M^i_{\text{float}} \|_1$ and/or $\| M^i_{\text{int32}} - M^i_{\text{float}} \|_2$.

Useful secondary metrics:

- cosine similarity of logits;
- top-1 agreement;
- top-5 / top-10 overlap;
- KL divergence between softmaxes, $D_{\mathrm{KL}}\left( \operatorname{softmax}(z_{\text{float}}) \,\|\, \operatorname{softmax}(z_{\text{int32}}) \right)$.

The core deliverable can just be the L1/L2 plots, though. KL/top-k are nice to have.

## Evaluation

Use a held-out prompt/input set that the student does not train on.

For each checkpoint, evaluate:

`checkpoint step
train logit L1
train logit L2
eval logit L1
eval logit L2
eval KL
eval top-1 agreement
eval top-5 overlap
per-layer/per-matmul L1/L2`

The important thing is to see whether training improves both train and held-out divergence.

## Desired result

The positive result would look like:

- naive int32 has noticeable divergence from float;
- training substantially reduces per-matmul divergence;
- final logit L1/L2 decreases steadily;
- held-out logit divergence also decreases;
- top-k agreement improves;
- the remaining divergence appears small and stable rather than concentrated in a few layers.

That would support the idea that we can keep the production model in floats while maintaining a separate int32 proof model that closely emulates it.

## Negative result

The negative result would be:

- per-matmul losses improve but final logits do not;
- final logits improve only on train data, not held-out data;
- one or two layers dominate the divergence and do not train away;
- int32 scaling/rounding creates sharp discontinuities that make optimization unstable;
- top-k behavior remains unstable despite low average L1/L2.

That would suggest either that the int32 representation is too constrained, the scaling scheme is wrong, or we need a different proof-model architecture rather than just a quantized copy of the float model.

## Deliverable

By the end, we want a small report with:

1. description of the float teacher and int32 student;
2. exact int32/fixed-point scheme used;
3. plots of logit L1/L2 over training;
4. plots of per-matmul L1/L2 over training;
5. comparison of naive int32 vs trained int32;
6. brief readout: does the trained int32 proof model get materially closer to the float production model?

The headline question is simply:

> Can training make the int32 proof model close enough to the float production model that the remaining divergence is small?
